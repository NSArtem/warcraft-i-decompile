# Unit combat, attack orders and building production (0x104b0..0x119c0)

The three objects at the front of war.exe's code segment, right after the
animation-script opcode stubs (0x103d2..0x104b0, `modules.toml`
"asm_blit_stubs"):

| module | range | what it is |
|---|---|---|
| `mod_104b0` | 0x104b0..0x110a0 | the combat core: damage formula, damage application to units and terrain, death, target acquisition, retaliation, and the target/stop/move order ticks |
| `mod_110a0` | 0x110a0..0x11530 | the attack order handlers (orders 5..8 of the order table at 0x5158c) plus the movement/approach helpers they use; 0x110a0 itself is 4 bytes of constant data |
| `mod_11530` | 0x11530..0x119c0 | building production: start/cancel research and training, the AI training choice, and the per-building production callbacks; 0x11530 itself is 8 bytes of constant data |

All three are "OPT" code (`-s -ot -ol -4r -zp2`, `docs/subsystems/codegen.md`);
the functions are 4-byte aligned inside the objects.

**Subsystem.** This is not the command layer and not the scenario start; it is
the unit/order layer the command layer calls into.  The evidence:

* the functions are the *callees* of the command and panel code:
  `UnitOrderTarget` (0x2e100) is called from here, and the panel starts
  research/training through these functions (0x2179d calls 0x11538, 0x217c1
  calls 0x115f4, 0x217e0 calls 0x116a8);
* the attack order handlers are the five pointers at 0x5159c..0x515ac, which
  are orders **4..8** of the unit order table at 0x5158c (index 2 = stop,
  index 3 = move, 0xa = harvest, 0xb = return goods; the command card passes
  those order numbers, docs/subsystems/status.md section 2);
* the only string this area references is `attack:1` (0x569d4), the
  `FatalError` tag of the order-4 slot - the object is an "attack" module of
  the unit code (the Insider's Guide list has no ATTACK.C, so the module
  names stay address-derived);
* the death path calls the score system (`ScoreOnMenKilled`,
  `ScoreOnBuildingKilled`, save_score.toml) and `UnitRemove`, and the damage
  formula reads the per-player upgrade rows documented in status.md
  section 3 - i.e. the game's actual combat rules run through this range.

Symbols: `analysis/symbols/mod_104b0.toml`; C: `src/mod_104b0/`;
declarations: `src/include/mod_104b0.h`.

## The unit record fields this area uses

The full record is in `docs/subsystems/game_2c4e0.md` (0x5c bytes, 200 entries
at 0x59640).  This area establishes or uses:

| off | type | use here |
|---|---|---|
| 0x0e | word | secondary flags: 0x10 "producing" (0x11538/0x115f4 set it, 0x116a8 tests it), 0x20 "cancel requested" (0x116a8) |
| 0x10 | word | main flags: 0x207 not a normal map unit, 0x80 dying/dead (0x10ee8 restarts production of a dead building), 0x4000 (0x1077c) |
| 0x12 | byte | target flag; bit 0x08 set when an attack order was issued, 0x10908 rewrites it to 4 |
| 0x16 | word | hit points (0x10650) |
| 0x1a | byte | energy/damage fraction: 0x106ec lowers it for the missile types, 0x110a4 tests it against 1/5, 0x11538/0x115f4 set it to 1 when production starts |
| 0x1b | byte | unit type 0..0x33 (>= 0x20 buildings) |
| 0x1e | byte | owner/player 0..4 |
| 0x1f/0x20/0x21 | bytes | order, next order, next order argument |
| 0x36/0x38 | words | timers (0x10650 skips victims with timer38, the idle scan tests timer36) |

| **0x3e** | byte | type/research row being produced (0x11538/0x115f4) |

| 0x52 | dword | target unit |

## Combat model

`UnitCalcDamage` (0x104b0) is the single damage formula (it is called both by
the melee strike 0x106ec and by the projectile spawn 0x11a10):

```
damage = unit_damage[type]            (0x51d5c)
bonus  = unit_damage_bonus[type]      (0x51d7c)
if type is 8/9: bonus += weapon_upgrade_bonus[upgrade row 0 & 0xf]
else:           damage += weapon_upgrade_bonus[upgrade row 1 & 0xf]
if a target unit exists:
    if Random(0xc) >= 0x6666: return 0          # the miss chance
    damage -= unit_armour[target->type]         (0x51c8c)
    damage -= armour_upgrade_bonus[upgrade row 9 & 0xf]
    damage = max(damage, 0)
else:
    if MapFlags(dest, 0xc) == 0: return 0       # nothing to hit
damage += bonus
return min(damage, 0xff)
```

The developer cheat (bit 2 of `cheat_flags`, 0x51214) short-circuits the
formula: when the owner's player type is 0 it returns 0xc8, otherwise 0.

The per-type tables (all 0x34 bytes except the two upgrade tables):

| table | what | evidence |
|---|---|---|
| 0x51c6c `unit_sight_range` | search/notice radius (1 mostly, 8 for types 4/5, 5 for 8) | (2r+1)-square scan in 0x10908, default order range in 0x2220c |
| 0x51d28 `target_priority` | target score base (0x69 for 4/5, 0x14 for buildings) | score = table - distance² in 0x10834 |
| 0x51d5c `unit_damage` | damage (0xff for the siege types, 13 for 6/7, 9 for 0/1) | 0x104e0 |
| 0x51d7c `unit_damage_bonus` | the second, armour-independent component (added after the clamp) | 0x104e6, 0x105b6 |
| 0x51c8c `unit_armour` | armour subtracted from the damage | 0x1055b |
| 0x51d9c `unit_projectile` | projectile type, 0x0c = melee | 0x106f8 |
| 0x51098 `weapon_upgrade_bonus` | {0,2,4} damage by weapon level | 0x104fd/0x1051b |
| 0x5109b `armour_upgrade_bonus` | {0,2,4} armour by armour level | 0x10568 |
| 0x51883 `hostility` | 5x5, 1 = enemy | row/column = owner |
| 0x510d8 `unit_type_callback` | per-type production callback | 0x119a3 |

Target acquisition (0x10908) keeps its state in one global struct at 0x58540
(`target_search`): best unit, the owner's hostility row, the origin tile, best
score, a flag, normal/extended range, chase flag, minimum range, the player's
visibility mask and the best distance.  The scan box is `2r+1` tiles wide with
`r = unit_sight_range[type]`, widened by 1 (player type 0) or 2 when nothing
was found inside the range; every object of the box goes through
`UnitConsiderTarget` (0x10834), which rejects dead/busy/invisible units and
keeps `target_priority[type] - distance²` (clamped up to 1) as the score.

Death handling (`UnitApplyDamage`, 0x10650): record the attacker
(`UnitSetLastAttacker`), subtract from hp, and when hp runs out award the kill
(men vs buildings by type 0x20), bump the per-player killed counter
(0x50dac/0x50db6), `UnitRemove` the victim and re-check the killer's target
(0x2207c).

## Attack orders (mod_110a0)

The order table at 0x5158c dispatches per `unit->order`; the five slots
0x5159c..0x515ac are this object:

| order | slot | handler | behaviour |
|---|---|---|---|
| 4 | 0x5159c | 0x1132c (AttackFatalStub, mod_104b0.toml) | `FatalError("attack:1")` - the "attack" order is a command mode, never a stored order |
| 5 | 0x515a0 | `AttackOrderTarget` 0x113e0 | validate/re-order the target (fn_2eefc with callback 0x20f84), call for help, strike |
| 6 | 0x515a4 | `AttackOrderHuman` 0x114d8 | order-6 entry: shared body with callback 0x20f30, flag 1 |
| 7 | 0x515a8 | `AttackOrderAtPoint` 0x11344 | retaliate, then move to the destination tile and strike there |
| 8 | 0x515ac | `AttackOrderAI` 0x114ec | AI entry: shared body with callback 0x20fac, flag = "small unit" |

`UnitAttackOrderTick` (0x1143c) is the shared body of orders 6 and 8: it checks
the target and re-issues the order through fn_2eefc, calls for help, runs the
siege crowding check for types 4/5, strikes when in range, and otherwise
wanders towards the last attacker or stops.  `UnitAttackStrike` (0x110a4) is
the "hit now" step (missile types only, gated on the energy byte);
`UnitWanderStep` (0x11298) faces a random direction and takes the first free
neighbouring tile; `UnitCheckAttackCrowding` (0x11140) limits the number of
friendly units around a siege target.  `UnitApproachPoint` (0x107a0) computes a
jittered tile in front of the target for the "go and attack" order.

## Building production (mod_11530)

The type-callback table at 0x510d8 (one dword per unit type) holds the
per-building production logic; the building slots (types >= 0x20, table base
0x510d8 + 0x80 = 0x51158) are:

| types | callback | what it does |
|---|---|---|
| 0x20/0x21 (farms), 0x32 | `NopProduction` 0x116c0 | trains nothing (a bare `ret`) |
| 0x22/0x23 (barracks) | `BuildingAutoTrain` 0x116c4 | weighted random choice among the four combat types the scenario allows, gated on a blacksmith and a mill |
| 0x24/0x25 (stable/kennel) | `TrainCavalry` 0x117f0 | trains types 0xc/0xd while `min(4, player_unit_cap) >= player_unit_count` |
| 0x26/0x27 (archery range) | `TrainArchers` 0x11848 | trains types 0xa/0xb under the same cap |
| 0x28/0x29, 0x30/0x31 (town hall) | `TrainWorkers` 0x118a0 | trains a worker (2/3) while below the worker cap |
| 0x2a..0x2f (blacksmith etc.) | `ResearchRangedUpgrade` 0x11910, `ResearchSpeedUpgrade` 0x11930, `ResearchArmourUpgrade` 0x11950 | the three research commands |

The parity of `type - 0x20` selects the race: even uses the table at 0x11534
{0,8,4,6}, odd the table at 0x11530 {1,9,5,7} (basic infantry, missile, siege,
mounted in that order, derived from the scenario mask bits 0, 4, 2, 3 and their
weights 4, 6, 2, 8 in BuildingAutoTrain).

Production start (`UnitStartResearch`/`UnitStartTraining`): refuse when
`flags2 & 0x10`; charge through fn_20d14/fn_20d74 unless `pay_resources`
(0x51120) is 0 (only `RestartProduction` clears it); store the type/row, the
build time (research_time 0x51876 / unit_train_time 0x51a14, fast-build cheat
bit 2 divides by 4), the cost cell in +0x46, set +0x1a/+0x3f/+0x40, set
`flags2 |= 0x10` and issue next order 0x10 (research) or 0x0f (training).
`UnitCancelProduction` (0x116a8) sets the cancel bit, and `RestartProduction`
(0x11990) re-runs the type callback with the payment suppressed (used by
UnitIdleTick for a destroyed building whose production word reached 1).

## Open questions

* **Order 4 and the 0x510a0 table.**  Order 4's handler is the
  `FatalError("attack:1")` stub, and `AnimEndDispatch` calls
  `order_handler_table[order]` at 0x510a0, whose slots 0..3 are zero in the
  image (no fixups) while 0x510b0..0x510c0 hold the five attack handlers.
  Either the animation-end opcode is only used by orders >= 4 (so the call
  lands in 0x510b0 and always reaches UnitAttackFrame) or 0x510a0 is patched
  at run time; no writer exists in the image.  Not resolved.
* **UnitWanderStep's loop.**  The original reads `[esp+ecx]` with ecx always 0
  and has no index increment, so only the {0} entry is ever tried; the
  reference C reproduces the observed behaviour.  Either the original source
  had a bug or the compiler hoisted an unrolled loop incorrectly.
* **`unit_damage` vs `unit_damage_bonus`.**  Both are per-type damage
  components and the formula adds both; the game meaning of the second
  component (a weapon bonus? a second attack mode?) is not documented in the
  guide.  The names are descriptive.
* **The building rebuild table 0x503a** is all zero in the image (filled per
  scenario); only the access pattern is known.
* **Module names.**  The ranges stay `mod_104b0`/`mod_110a0`/`mod_11530`;
  the code and the `attack:1` tag support an "attack/unit orders" module, but
  no name from the Insider's Guide list can be assigned with evidence.

## Change requests

1. **Discovery (tools/wc1/analysis.py).**  The module starts 0x110a0 and
   0x11530 are constant data, not functions; discovery seeds every object
   start, so `make progress` counts two non-functions.  A veto like the
   0x24860 one (a start whose bytes are a data array referenced by an
   absolute load, here 0x112a3 `mov ecx,[0x110a0]`) would remove them.  Until
   then the data entries exist only in this TOML (func and data tables are
   separate, so `wc1.symbols` stays clean).
