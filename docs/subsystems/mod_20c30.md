# mod_20c30: the build/placement box (PLACEBOX.C), the layer helpers and the packet tail

The area covers three adjacent objects at the top of the game-code block:

| module | range | what it is |
|---|---|---|
| `PACKET.C` tail | 0x21c20..0x21ce8 | the four small fixed-format message senders (control, cheat word, chat text, save/load sync) |
| `mod_21cf0` | 0x21cf0..0x21de4 | `LayerAdd` / `ResourceFreeBody`: register a bitmap as a screen layer, free a resource body.  Named `LayerAdd`/`LayerFree` by status.h; playflic.toml names 0x21cf0 `ResourceFreeBody` |
| `PLACEBOX.C` | 0x21df0..0x22c50 | the "Select location" build/placement UI and the order-3 move handler it drives |

This file documents 0x21c20..0x22800 (the assigned range: the whole placement
*start/update* side plus the packet tail and both layer helpers).  The tail of
PLACEBOX.C (0x22800..0x22c50: `PlaceBoxCancel`, `PlaceBoxConfirm`,
`PlaceBoxCreateBuilding/Road/Wall`) is a separate area; it is described here
where the flow needs it, with its addresses, but not claimed.

Symbols: `analysis/symbols/mod_20c30.toml`.  C: `src/mod_20c30/`.
Declarations: `src/include/mod_20c30.h`.  Tests: `tests/test_mod_20c30.py`.

The unit record is the one in `docs/subsystems/game_2c4e0.md`, the order table
in `docs/subsystems/mod_13f60.md`, the packet dispatcher in
`docs/subsystems/packet.md`, the layer/bitmap library in
`docs/subsystems/graphics.md`.

## 1. The flow: from the command card to a building

```
command card "Build" (CMD.C)
   -> PlaceBoxStart(type)              0x22798   first half of this range
        cost check + payment           fn_20d74 (0x20d74)
        state: place_type[player], place_active[player] = 1
        bitmap/layer + mouse handlers + palette cycle
        "Select location"              (0x572dc)
   -> [every frame] PlaceBoxUpdate     0x2261c
        mouse -> map tile, PlaceBoxCheck, redraw the box
        -> PlaceBoxCheck(type, tile)   0x2256c
             road 0x34 -> fn_13360, wall 0x35 -> fn_1346c, else fn_1357c
   -> click release -> PlaceBoxRelease 0x1b4dc -> NetSendPlaceConfirm 0x21b24
        (packet type 6; PACKET.C area)
   -> PlaceBoxConfirm(p)               0x22ae4   other area
        re-check, PlaceBoxCancel, then
          type <= 0x32 -> PlaceBoxCreateBuilding 0x229c8  (UnitCreate)
          type == 0x34 -> PlaceBoxRoad           0x22a4c
          type == 0x35 -> PlaceBoxWall           0x22a98
   -> the worker gets an order-3 (move) order to the site; the build itself is
      the order's callback (fn_210dc / fn_21094)
```

`PlaceBoxStart` only continues past the state store on the machine that owns
the local player: it returns early when `net_event_pending` (0x5a11a) is
non-zero (0x2281e).  The box/bitmap/palette work is therefore local; the two
machines each run their own copy of the flow through the shared packet
dispatcher (types 4/5/6, `fn_215f0` jump table `cd_215a8`).

## 2. Map coordinates and the box overlay

* Tile = `(map_scroll_x + ((mouse_x - 0x48) >> 4), map_scroll_y + ((mouse_y - 0xc) >> 4))`
  (0x22677-0x226aa).  The map view starts at screen x 0x48, y 0xc; a tile is
  16 pixels.
* Outside `mouse_x-0x48 >= 0xf0` or `mouse_y-0xc >= 0xb0` the box is hidden
  (`layers[21].active = 0`, 0x22669).
* The box lives in **layer 21** (`layers` 0x5aa90 + 21*18 = 0x5ac0a): active
  word at 0x5ac0a, x/y at 0x5ac0c/0x5ac0e, w/h at 0x5ac10/0x5ac12, data at
  0x5ac14, callback at 0x5ac18.
* Its bitmap is `place_box_bm` 0x52b24 (`{w,h,data}`; data at 0x52b28 is a
  GdsAlloc(0x900) buffer - 48x48, the 3x3-tile maximum).  `PlaceBoxInit`
  0x224e0 allocates it and clears `place_active[2]`; `PlaceBoxShutdown` 0x2254c
  frees it.
* The box size in pixels is `unit_type_size[type].w * 16` by `.h * 16`
  (0x2283f-0x2285f and 0x226c8-0x226db).
* Drawing: `draw_color` (0x5ad30) is 0xda on a legal tile and 0 on an illegal
  one (0x226de-0x226ec); the border is two `Line` calls (1,1)-(w-2,h-2) and
  (w-2,1)-(1,h-2) (0x2270b-0x22726).  While the box moves the palette cycle
  0x0f animates its colour between `place_colors_bad` (0x50bbc) and
  `place_colors_ok` (0x50c1c) through `palette_cycles[15].list` (0x6295b =
  0x628a0+15*12+7; 0x2272b-0x22756).
* `map_cursor_flags` (0x5a7c9) bit 0 is set while a box is up; the map draw
  tests it (UnitsDraw 0x2dc46).

## 3. Tile checks, tile occupancy and the error messages

`PlaceBoxCheck` 0x2256c returns a code 0..5 that indexes `place_error`
(0x52bc4):

| code | message |
|---|---|
| 0 | - (legal) |
| 1 | "You cannot build off the map" (0x52b2c) |
| 2 | "You cannot build there" (0x52b49) |
| 3 | "You must build near cobbled road" (0x52b60) |
| 4 | "You must build near your buildings" (0x52b81) |
| 5 | "You must explore there first" (0x52ba4) |

The check itself dispatches on the type byte (0x225b3-0x225f2): road 0x34 ->
`fn_13360`, wall 0x35 -> `fn_1346c`, every other type -> `fn_1357c` (all in
mod_13270; out of this area).  Before the call the selected worker's own tile
is marked free (clear map_flags bit 8 of its cell, 0x225a8) and afterwards
restored (0x2260a), so a worker standing on the site does not veto it.

Tile occupancy is the `map_flags` word array (pointer at 0x5857c, 64x64,
`y*64+x`): bit 8 (0x100) = a unit stands here, bits 0x207/0x1000/0xf000 are
the unit state bits (game_2c4e0.md).  `object_map` (pointer at 0x58580) holds
the unit pointer per cell.  Road placement sets the per-owner bit
`owner_block_mask[player]` (0x51dca, {1,2}) through `fn_2c100`.

The placement flow's own occupancy test is `TileOccupiedByUnit` 0x21ec0: for
the destination tile it returns 0 when there is no object, 1 for a non-map
unit, 0 for an enemy, 0 for a non-passable friendly, then 0 unless the
occupant is moving, and finally 1 when that occupant's next path step is *not*
the unit's tile.  `MoveOrderTick` uses 1 as "the destination is settled, do
not reset the path".

`UnitIsPassable` 0x21e58 is the underlying predicate: a unit is passable when
it is not a map unit and type <= 0x1f, or (for a map unit) when its order is 3
(move) or 0xc, its `flags2` nibble 0xf000 is clear and flag 0x1000 is clear.

## 4. Cost checks

`fn_20d74(owner, pay, type)` 0x20d74 charges or refunds the gold/lumber of a
unit type (`score_value*10`, `unit_lumber_cost*10`), checks the food cap
(`player_active_men - player_summoned` against `player_food`) for non-building
types, and **returns a message string** on failure (0 = paid):

* `PlaceBoxStart` calls it with `pay = 1` (0x227d9) and, on failure, shows the
  returned string with `fn_19f70(msg, 0x24)` (0x227f0).
* The confirm side pays again (`PlaceBoxConfirm` 0x22be3) and `PlaceBoxCancel`
  refunds with `pay = 0` (0x22967).

The cost is therefore paid when the box is opened, refunded on cancel and
charged a second time on confirm - matching the two-step "select then place"
UX (a cancel returns the money, a confirm re-pays so the first payment acts as
a reservation).

## 5. The placement dialog and its mouse handlers

`GameScreenInputInit` installs two indirect map handlers: the left-press slot
`map_press_handler` (0x59510, called through 0x1a14c) and the left-release
slot `map_release_handler` (0x59518, through 0x1a130).  The placement box
swaps both:

| slot | normal | placing |
|---|---|---|
| press 0x59510 | `MapPressDefault` 0x1b578 | `PlaceBoxPress` 0x21af8: sends a 3-byte packet type 5 (cancel) and locks the panel |
| release 0x59518 | `MapReleaseDefault` 0x1b448 | `PlaceBoxRelease` 0x1b4dc: resolves the tile under the mouse and calls `NetSendPlaceConfirm` 0x21b24 (packet type 6) |

`PlaceBoxCancel` restores both, disables palette cycle 0xf, deactivates layer
21, deselects (`fn_25b6c(0)`), clears the message line and `map_cursor_shape`
(0x59520).  The two other placement packets come from `fn_215f0`: type 4 ->
`PlaceBoxStart(type)` (0x21680), type 5 -> `PlaceBoxCancel` (0x21695), type 6
-> `PlaceBoxConfirm(point)` (0x21666).  All three run `StatusPanelLockAdjust`
first, so the status panel is locked while any placement is open.

## 6. The order-3 move handler (and why it lives here)

`OrderUpdateMove` 0x222e8 is entry 3 of the order dispatch table (0x51598,
mod_13f60.md).  It is the piece that carries workers to a build site:

1. `UnitMoveOrderCheck` 0x11004 (mod_104b0) - a human unit may pick up a fight.
2. `UnitClearTargets` 0x2207c drops a dead/timed-out target or attacker.
3. When the queued argument is not in range (`OrderTargetInRange` 0x2220c),
   `PathFind` 0x2cc54 builds a path; on failure `WorkerReturnToMine` 0x21df0
   sends a worker back to the mine (or the unit stops).
4. `PathAdvanceFacing` 0x2c538 either takes one step or `MoveOrderTick`
   0x21f90 handles arrival: blocked destination -> re-issue or reset,
   `flags2 & 0xf000 >= 0xf000` -> done (stop), `TileOccupiedByUnit` -> settle,
   otherwise reset.

`UnitOrderTargetFinish` 0x22464 is the tail of `UnitOrderTarget` 0x2e100: it
clears the path, clamps the destination (`PathSetReachableDest` 0x223bc walks
the path trace back to the last walkable tile), and decides whether a two-step
order (a queued (order, argument) pair such as move-then-attack) promotes its
argument to the current order now - using `order_props` (0x534f4, bit 1),
`OrderTargetInRange`, and `UnitSetNextOrder` 0x2eeac.

`OrderTargetInRange` 0x2220c takes the range from `order_range` (0x52b04; 0xff
= `unit_sight_range[type]`, and for a target-less move that only applies when
the destination tile is a legal walk target), clamps the destination with
`OrderClampDest` 0x220e8 (centre on a building target, then keep it within half
the building's extent of the unit), and requires both |dx| and |dy| <= range.

The T4 blockers are all codegen/register-allocation differences (each entry
records the first differing byte).  Two families recur:

* **dword-view short loads** - the original reads a `short` field as
  `mov eax,[field-2]; sar eax,0x10` where 10.0a emits `movsx ax,[field]`
  (WorkerReturnToMine, MoveOrderTick; the same idiom is unmatched in
  `PathAdvanceFacing` 0x2c538).  The idiom *is* reproduced by writing the
  value through a long view; `LayerAdd` uses that (`RECT_WORD` in
  `layer_add.c`) and matches.
* **16-bit locals** - the original keeps coordinates in 2-byte frame slots
  (`mov [esp+4],ax`); 10.0a keeps them 32-bit (PlaceBoxUpdate).

## 9. Source idioms that made the matches

* `LayerAdd`'s size multiply must read the packed `Rect` pair through a long
  view (`*(long *)((char *)r + off - 2) >> 16`); `r->w * r->h` gives `movsx`.
* `UnitIsPassable` returns **unsigned short** - that is what turns the
  `setle al` into `xor ah,ah` instead of `and eax,0xff` (0x21e79).
* `ResourceFreeBody` takes a `Bitmap *` (so the body load lands in ebx, as in
  the original) rather than a `void *` with a byte-offset load.
* `PlaceBoxInit` clears `place_active` through the runtime `__STOSB`
  (0x34390) with its asm convention (dst=eax, val=edx, count=ecx); a normal C
  declaration or the compiler's `__STOSB` builtin puts the count in ebx and
  calls `__STOSB_`.
* The order setters/clearers return **unsigned short** (`UnitMoveOrderCheck`,
  `PathFind`, `UnitAdvanceOrder`, `fn_2207c`, `fn_2220c`): with an `int`
  declaration the caller's `test ax,ax` becomes `test eax,eax` and shifts the
  whole function.

## 10. Open questions

* 0x59bd0..0x59bd5 are documented as `place_*[2]` because every read is
  indexed by `net_event_pending`; the write at 0x22805 uses the same index,
  so in a link game each machine owns one slot.  Why the *local* box only ever
  draws `place_active[0]` (0x22624) and `place_type[0]` (0x226ad) is
  unresolved - either the local player is always slot 0, or the box is drawn
  for the first pending placement only.
* `PlaceBoxCheck`'s second occupancy restore (0x2260a) re-tests the worker and
  masks bit 8 with `or`: the exact map_flags bit (0x100) differs from the one
  the path code uses for "blocked" (0x2000, 0x8000).  The bit definitions of
  map_flags outside 0x100 are still open (game_2c4e0.md).
* `fn_13360`/`fn_1346c`/`fn_1357c` (the three tile checks) are in mod_13270
  and not reconstructed; they are the only place the "cobbled road" and
  "near your buildings" rules live.
* `PlaceBoxWall` writes the build site into the worker's +0x42 and starts
  production of pseudo-type 0x35 - the wall production path is in STATUS.C's
  training code and deserves its own check.
