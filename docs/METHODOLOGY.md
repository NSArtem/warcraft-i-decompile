# Methodology: evidence, confidence, verification

The goal is a source reconstruction where every claim can be checked. Guessed
code is never presented as verified, and every name is a claim with evidence.

## Verification tiers (what the pipeline proves mechanically)

| Tier | Claim | Mechanical check | Command |
|---|---|---|---|
| T0 Format | The LE parser reproduces the loader's view of war.exe | 8770 fixups decoded, objects/entry/stack checked | `pytest tests` |
| T1 Round-trip | The generated asm *is* the program | asm assembles (flat, original addresses) to a byte-identical image of both objects | `make roundtrip` |
| T2 Relink | The toolchain reproduces the executable | wlink output is load-equivalent to the original: same objects, entry, stack, every fixup, identical loaded image | `make build` + `python3 -m wc1.compare` (C objects are linked in place, so this holds with matched C too; docs/subsystems/build.md) |
| T3 Match | A C function is the original function | wcc386 output identical in code bytes, every relocation resolves to the same target, module-local data identical | `python3 -m wc1.match src/x.c` |
| T4 Equivalent | Non-matching C behaves identically | differential execution (unicorn harness, same inputs → same outputs/memory effects); tests documented next to the function | (per function, see tests/) |
| T5 Behavioural | The hybrid build behaves like the original | headless DOSBox-X runs and screenshots/state comparisons | `make run`, `python3 -m wc1.run` |

## Confidence levels (for names, types, prototypes and module assignments)

| Level | Meaning | Minimum evidence |
|---|---|---|
| `verified` | Proven by a mechanical check | `verified_by` names the check: `match:` (T3), `libsig:` (byte-identical to a known library), `difftest:` (T4) |
| `high` | Several independent lines of evidence agree | e.g. a string the function prints + argument use at callers + behaviour of its body |
| `medium` | One strong piece of evidence | e.g. the function's body unambiguously implements X |
| `low` | Plausible from context | e.g. called from the save routine and writes to a file |
| `speculative` | Placeholder hypothesis | Allowed, but must say why |

Rules:
* Evidence entries cite addresses (`0x1d330`), strings, observed runtime
  behaviour (with how it was observed) or external references (see
  `docs/REFERENCES.md`).
* A name copied from an external reference (e.g. the Insider's Guide module
  list) is evidence for *that name existing*, not for which code it denotes.
  Module assignments need their own evidence.
* When evidence contradicts an existing claim, downgrade or fix the claim and
  record the correction in the evidence list (do not silently overwrite).
  Example: `fn_30e38` was first guessed as `strupr`; its arithmetic maps A–Z
  to a–z, so it is `strlwr` (see `analysis/symbols/clib.toml`).
* Ghidra/decompiler output is a *hint*, never evidence by itself.

## Source of truth

* `analysis/symbols/*.toml` — names, prototypes, types, evidence, confidence.
  Validated by `python3 -m wc1.symbols`.
* `analysis/raw_insns.txt` — instructions NASM cannot encode identically
  (regenerated by `make roundtrip`).
* `src/**/*.c` — reconstructed C. A function's DB entry gets `src = "src/x.c"`
  only once `wc1.match` reports MATCH (or a T4 test exists and confidence is
  set accordingly); the build then takes that function from C.
* `docs/` — subsystem and format documentation, each claim with evidence.

## What is never committed

The original game files and anything that reproduces them in bulk (the
generated `build/war.asm`, extracted data). The repo contains tools, evidence,
and reconstructed source; everything else is regenerated from the user's own
copy (`make extract`).
