# mod_13f60: the unit order dispatch and the two-player setup menu

Area = `mod_13f60` in `analysis/modules.toml`, **0x13f60..0x16390**, 68
discovered functions, "OPT" code (`-s -ot -ol -4r -zp2`).  Names, prototypes
and per-address evidence: `analysis/symbols/mod_13f60.toml`; reconstructed C:
`src/mod_13f60/`; declarations: `src/include/mod_13f60.h`; tests:
`tests/test_mod_13f60.py`.

The range is **two source files** whose boundary (0x145e6) is visible in the
code itself:

| part | addresses | what it is | guide name [R1] |
|---|---|---|---|
| A | 0x13f60..0x145d0 | the per-order update handlers of the unit dispatcher (one function per unit order, called from the tick) | `DISPATCH.C` |
| B | 0x145e6..0x16390 | the two-player / custom game setup menu: main menu, game-type, campaign, army, map and race dialogs, the modem/serial/network settings, and the state machine that runs them | `DLGS.C` / `DLG_SET.C` |

Evidence for the split: part A ends with the `'dispatch:5'` FatalError stub
(0x145d0) that the last two entries of the order table point at, and part B
starts with the initialised parameter records of dialog 0x180 (`cd_145f0`
0x145f0, `cd_1461c` 0x1461c, `cd_14668` 0x14668) that no code in part A
references.  `analysis/modules.toml` records the same `'dispatch:5'` tag and
the module's string pool slice 0x56ab8..0x56bd1.

## 1. Part A: the unit order dispatch (DISPATCH.C, 0x13f60..0x145d0)

The unit tick `0x2ec0c` walks the 200-record unit array and, for every unit
that passes its visibility/pathing guards, calls

```c
    call dword [order_update_table + unit->order * 4]     /* 0x2ed0f-0x2ed19 */
```

with the unit in `eax`.  A **non-zero return means "order finished"**: the tick
then calls `0x2edac` (`UnitAdvanceOrder`: adopt the pending order from
`+0x20`/`+0x21`, play the order sound from `0x5328c`) and, when that returns
non-zero, `0x2edac` again for the next one.  A zero return keeps the order.

`order_update_table` (0x5158c, 32 dwords, all fixups into code object 1):

| order | handler | order | handler |
|---|---|---|---|
| 0x00 | 0x13f60 `OrderUpdateGone` | 0x10 | 0x14534 `OrderUpdateResearch` |
| 0x01 | 0x13f68 `OrderUpdateDeath` | 0x11 | 0x14140 `OrderUpdateSpell` (healing) |
| 0x02 | 0x14030 `OrderUpdateStop` | 0x12 | 0x14140 (far seeing) |
| 0x03 | 0x222e8 (move, mod_20c30) | 0x13 | 0x14140 (invisibility) |
| 0x04 | 0x1132c FatalError `'attack:1'` | 0x14 | 0x14140 (raise dead) |
| 0x05 | 0x113e0 (mod_110a0) | 0x15 | 0x14140 (unholy armor) |
| 0x06 | 0x114d8 (mod_110a0) | 0x16 | 0x14140 (summon water elemental) |
| 0x07 | 0x11344 (mod_110a0) | 0x17 | 0x14140 (summon daemon) |
| 0x08 | 0x114ec (mod_110a0) | 0x18 | 0x14140 (summon spiders) |
| 0x09 | 0x141d0 `OrderUpdateHold` | 0x19 | 0x14140 (summon scorpions) |
| 0x0a | 0x1cd90 (harvest, mod_1c...) | 0x1a | 0x14140 (rain of fire) |
| 0x0b | 0x1cf5c (return goods) | 0x1b | 0x14140 (cloud of poison) |
| 0x0c | 0x1d034 | 0x1c | 0x13fe8 `OrderUpdateAppear` |
| 0x0d | 0x1d1e0 | 0x1d | 0x14084 `OrderUpdateJoin` |
| 0x0e | 0x141e0 `OrderUpdateRepair` | 0x1e | 0x145d0 `DispatchFatal` |
| 0x0f | 0x143cc `OrderUpdateProduce` | 0x1f | 0x145d0 `DispatchFatal` |

The order *ids* are fixed by the code that writes them, not by guessing:

* order 2 = stop (`UnitSetOrder(u,2)` from UnitRemove 0x2e166/UnitCreate
  0x2e855 and the stop button's command mode 2 at 0x20e9a),
* order 0x0e = repair (the repair button 0x2110c sets command mode 0x0e),
* order 0x0f = train/build (0x11696 after the gold/lumber payment;
  docs/subsystems/status.md reads "training a…" for it),
* order 0x10 = research (status.md),
* orders 0x11..0x1b = the eleven spell ids of the command card (`healing`
  0x11 … `cloud of poison` 0x1b; SPELL.C sets 0x16/0x19 at 0x2a96c/0x2a986),
* order 0x1c is written only by `UnitCreate` 0x2e6f4 for a new **skeleton**
  (type 0x1a, 0x2e819-0x2e828),
* order 0x1d is written only by the same function for a **neutral** (owner 4)
  non-building unit that is created with 5 hp (0x2e92e-0x2e93b).

### 1.1 the handlers, one by one

`OrderUpdateGone` (0x13f60, order 0) re-runs `UnitRemove` 0x2e96c every tick
(draw-list removal, owner → neutral, flags) and never finishes.  It is the
resting state of a unit that is off the map.

`OrderUpdateDeath` (0x13f68, order 1) is the dying state (UnitRemove sets
order 1 at 0x2e166).  Buildings go through `fn_13860`/`fn_2bdd4`; a normal unit
whose `death_sound_by_type[type]` (0x5156c) is non-zero becomes a neutral
type-0x33 corpse (owner 4, `+0x1b` = 0x33, `+0x7` = 0) and plays sound 1 or 2
through `UnitStartAnim`; the next tick takes the type-0x33 branch and hands the
corpse to order 0.

`OrderUpdateStop` (0x14030, order 2) runs `fn_10ee8`, then finishes the
harvest swing animation (`fn_298a0`) when the work word `+0x14` is set, else
turns an idle unit (`UnitIdleTurn` 0x13ff0) unless it has a pending order or is
a catapult (type 4/5).

`UnitIdleTurn` (0x13ff0) is the only non-handler helper of the group: with
`GameRandom(0x1b) & 0xff` it turns the unit one step left (value 0) or right
(value ≤ 3) on the 8-direction ring at `+0x8`.

`OrderUpdateHold` (0x141d0, order 9) clears the chase target `+0x3a` and sets
the animation timer `+0x6` to 0xff, returning "not finished" forever.
*Low confidence on the command that selects it*: no site stores 9 into the
order bytes, so the name describes the body.

`OrderUpdateJoin` (0x14084, order 0x1d) is the "wounded unit joins the player"
state.  `fn_13a90` 0x13a90 scans the 3×3 object map around the unit and reports
whether a **player-0** unit is adjacent; while the unit has ≤ 5 hp and nobody is
near it just turns (except the type 0xf/0x10 heroes).  Once a player unit is
adjacent it clears the five per-player words at 0x50e54 (and 0x50e4a = 1),
uncounts the old owner (`fn_13c84`), converts **type 0x10 "Wounded" into type 8
"Archer"**, sets owner 0, recounts (`fn_13c04`), stops palette cycling, sets
`[0x500de] |= 1`, issues a stop and finishes.

`OrderUpdateRepair` (0x141e0, order 0x0e): the target at `+0x52` must be alive
and not at full `unit_max_hp[type]`; the owner must have gold (0x50074) and
lumber (0x50060).  Each step adds 8 hp (clamped), bumps the repair counter at
`+0x52` and, when it passes 1, charges one gold and one lumber.  With no
resources the peasant is stopped and the local player sees
*"Need lumber to finish repairs"* (0x56ab8) or *"Need gold to finish repairs"*
(0x56ad8) — the pair fixes which array is which: **0x50060 = lumber,
0x50074 = gold**.

`UnitWorkProgress` (0x14334) is the shared progress routine of the two
building orders: it counts down `+0x3f`, advances the progress byte `+0x40`,
recomputes the frame fraction `+0x1a = 255*progress/duration`, and on completion
clears `+0x1a`/`+0x40`, clears `+0xe` bit 0x20 and issues a stop.  The
`status_dirty` word (0x5a2d0) is raised while the work runs.

`OrderUpdateProduce` (0x143cc, order 0x0f): when the work bit 0x20 is set the
product is finished — 7.5×`score_value[type_copy]` is added to the owner's gold
and 7.5×`unit_lumber_cost[type_copy]` to the lumber (the 30/4 sequence at
0x1440e…0x14450), the wall type 0x35 clears the map-flag bit 0x10, other types
place the new unit (`fn_2c14c` / `fn_2e650`) and the owner's per-type counter
`0x50d84` is decremented.

`OrderUpdateResearch` (0x14534, order 0x10): same progress routine, then
`ResearchCost(owner, type_copy, &level)` and 3×level/4 gold added; the
"research done" path bumps the level byte.

`OrderUpdateSpell` (0x14140, orders 0x11..0x1b): stores the spell id in
`spell_order` (0x5a7c0), selects the target handling from the per-order
property byte `0x534f4[order]` (bit 0 = needs a target, bit 2 = a unit target,
bit 1 = "issue an order target"), sets the facing (`fn_1def0`), runs
`fn_27aa4` and clears `spell_order`.

`OrderUpdateAppear` (0x13fe8, order 0x1c) completes immediately (`return 1`).

`DispatchFatal` (0x145d0) is the `FatalError("dispatch:5")` default that entries
0x1e/0x1f point at; the tick never dispatches those values.

## 2. Part B: the setup menu (DLGS.C, 0x145e6..0x16390)

`SetupMenuLoop` (0x162b0) is one state machine:

```c
    screen_buf = GdsAlloc(0x12c0);            /* 0x5165c */
    load the dialog art (resource 0xf6), init layer 0x0f, the sound table, music
    while (setup_state != 0x10)
        call state_table[setup_state](unit?);  /* 0x16357-0x1636c */
    free everything
```

`state_table` = 0x51718, 16 entries:

| state | function | dialog resource | what it does |
|---|---|---|---|
| 0 | 0x15588 `MainMenu` | 0x105 | Replay introduction / Start a new game / Load existing game / Quit to DOS |
| 1 | 0x15644 `PlayIntroduction` | – | `SetGameMode(0)`, leave the menu (the intro plays in mode 0) |
| 2 | 0x15668 `SelectGameTypeDialog` | 0x17c | Single Player / Modem / Network / Direct-Link / Cancel |
| 3 | 0x15764 `LoadGameDialog` | 0x174 | the seven save slots, Load Game / Cancel |
| 4 | 0x157e8 `ChooseCampaignDialog` | 0x17d | Orc Campaign / Human Campaign / Custom Game / Cancel |
| 5, 6 | 0x15898 `CustomGameMenu` | 0x17f (single), 0x186 (link) | Set Race / Set Army / Set Map / Ok / Cancel (Start / Hang Up when linked) |
| 7 | 0x1599c `SetArmyScreen` | 0x192+race, 0x18e+2·race+side | the "Set Army" screen with the scenario preview |
| 8 | 0x15b30 `SetRacesScreen` | 0x196 / 0x197 | Set Player Races |
| 9 | 0x15bc0 `SetMapScreen` | 0x180 | Set Map: Forest / Swamp / Dungeon / Random |
| 0xa | 0x15ca8 `ModemConnectionDialog` | 0x182 | Modem Connection (phone, baud, COM, IRQ, Setup) |
| 0xb | 0x15e1c `ModemSetupDialog` | 0x183 | Modem Setup (the three AT command strings, Tone/Pulse) |
| 0xc | 0x15fbc `NetworkConnectionDialog` | 0x185 | Network Connection (node number 0..99) |
| 0xd | 0x16044 `DirectConnectionDialog` | 0x184 | Direct Connection (baud, COM, IRQ) |
| 0xe | 0x160f0 `NetGameStart` | 0x18d | `NetLinkStart`, the "Connecting…" dialog, side/race setup |
| 0xf | 0x16278 `ConnectionFailed` | 0x176 | the connection-failure box |
| 0x10 | – | – | end of the menu |

The button labels above are decoded from `DATA.WAR` (resource id − 2 is the
archive index, `[R]` in docs/subsystems/resources.md); the dialogs' text
carries `@1X@2` hotkey-colour escapes.  The **case order of each dialog is the
control order in the resource**, which is not always the order the labels
appear in (Ok/Cancel are usually first); the case comments in
`analysis/symbols/mod_13f60.toml` name the button each case handles.

### 2.2 the parameter records

Three initialised records live in the code object and are copied into globals
at run time (`NetGameStart` copies `cd_145f0` and `cd_1461c` at 0x16115):

* `map_choice_params` (0x5160c, 11 dwords) — dialog 0x180's block:
  `{long map; void (*choose[4])(struct Dialog *); long count = 3;
  void (*refresh)(struct Dialog *); long pad[4]}`.  The four choose
  callbacks are `fn_150f0(d, n)` wrappers for n = 0..3 (Forest, Swamp,
  Dungeon, Random) and `refresh` re-applies the stored selection.
  `fn_150f0` swaps the current "page" of a list object (`[d+6]`: the head dword,
  the count word at +0x14 and the page table at +0x1c) and then re-points the
  record found by walking `[d+0x26]` in 0x1c-byte steps to the n-th
  `-1`-terminated run of `[d+0x1a]`.
* `net_settings` (0x51638, 8 dwords) — dialog 0x182's block:
  `{long side; long baud_index; short port; long irq_index;
  fn SetIrq (0x1550c); fn PhoneNumberLoad (0x15568); fn PhoneNumberSave (0x15558); long 0}`.
  The dialog unpacks it into `net_side` 0x52a50, `modem_port` 0x52994,
  `modem_baud` 0x52990 (through `BaudToIndex`) and `modem_irq` 0x52996, and
  writes the phone number to 0x52a28.
* `army_setup` (0x51660, 19 dwords) — the "Set Army" block:
  `{long count[14]; char *label[2]; fn toggle (0x14e48); fn labels (0x14d68);
  fn totals (0x14d04)}`.  The 14 counts are two sides × seven unit rows; the
  screen's dialogs are 0x192/0x193 (single player) and 0x18e..0x191 (linked,
  two races × two sides); `ArmyTotalsText` sums each half (`v−1` for `v > 1`)
  into the two label buffers `dat_59230`/`edit_buffer1`.

### 2.3 the save-slot files

`SaveSlotPath` (0x14740) builds `<exe_dir>\save<n+1>.sav`, or `.net` for a
linked game; `SaveSlotCreate` (0x14ad8) writes the slot header (0x20-byte name
with a 0x1a tail byte, 0, 0, `'War1'`), `SaveFileChecksum` (0x14670) folds the
image from offset 0x2c into `sum = (sum + dword) * 2`, `SaveFileFinish`
(0x146cc) writes that checksum at 0x20 (or deletes the file), `SaveSlotsScan`
(0x147a8) fills the seven 0x20-byte labels at 0x592e8 from the files (or
`[remote slot]` for the other machine in a linked game) and `SaveSlotOpen`
(0x1498c) re-opens a slot after validating the magic and the checksum.
The on-disk layout is `docs/subsystems/save_format.md` section 1 — that
document was written from `mod_24860`'s writer/loader and these functions are
the other half of the same format.

`SaveSlotsScan` has a **second entry point** at 0x14960 (the label-copy block)
that the initialised record `cd_14668` (0x14668) points at next to 0x147a8.
Code discovery does not promote it (it lies inside 0x147a8's extent and is only
reached through that data pointer), so it has no symbol entry; see the change
requests.

`SaveSlotPath` 0x14740 (T3 above) is compared by
`test_save_slot_path` (`tests/test_mod_13f60_t4.py`) only with `sprintf`/
`_makepath` stubbed: the original's `sprintf` (0x31be2) is a segmented
routine of the 10.0a runtime that the flat unicorn harness cannot run
(`strlen` 0x31d1a fails the same way at 0x31d2d).

Named only (no C): the other 44 functions — the order handlers need the unit
record plus `fn_10ee8`/`fn_298a0`/`fn_2c14c`/`fn_2e650`/`UnitStartAnim`… to be named
first, and the menu functions are dominated by `RunDialog` 0x180a8 (the dialog
engine, mod_16390) and by the layer/bitmap API.

Source idioms the matches needed (10.0a):

* the dialog control record is **packed**: a pointer at `+0x06` and the text
  pointer at `+0x16` (`struct Control` in `src/include/mod_13f60.h`, `-zp2`);
* a field that the original reads through an *aligned dword + shift* must be
  declared as that dword (or it compiles to `movsx`); `SetGameMode` is the one
  case in this area and stays reference C;
* `IsNumberChar`/`IsPhoneChar` return **short**: the caller tests `test ax,ax`
  and the `return 0` of `IsPhoneChar` has no code at all (the fall-through
  leaves `ax` = 0);
* the numeric-field callbacks compare the `atoi` result **as an `unsigned
  short`** (`xor edx,edx; mov dx,ax`), and `edit_value = 0` then comes out as
  `xor edx,eax` because both operands are known to be 99.

## 4. Open questions

* **Order 9** (`OrderUpdateHold`): no writer of order 9 exists, so the command
  that selects it is unknown (the body is clear).  Orders 0x0c/0x0d
  (0x1d034/0x1d1e0) and 0x05..0x08 are outside this area and still unnamed.
* **Order 0x1c/0x1d** are written only by `UnitCreate` for a skeleton and for a
  neutral 5-hp unit; the campaign script role of the latter (the "wounded unit
  that joins") is inferred from the handler, not from the scenario data.
* `army_setup`'s 14 counts: the dialog labels give seven unit rows per side,
  but the exact unit types behind each row are not established (the labels are
  shared by both races).
* The second entry point of `SaveSlotsScan` (0x14960) has no symbol (see the
  change requests).
* `map_choice_params`' page mechanism (`fn_150f0`) is described structurally;
  what the four "pages" of the list object are at run time is not known.
* `net_node_number` (0x52a7c) is written by the dialog and read nowhere in
  war.exe, so its consumer (an IPX/NetBIOS driver) is outside the executable.

## 5. Change requests (not applied - shared files / other areas)

1. **Code discovery** (`tools/wc1/analysis.py`): promote a data-pointer target
   that lies inside another function's extent when the pointer comes from an
   in-code data table *and* the target is preceded by a terminator
   (`ret`/`jmp`) — 0x14960 (referenced by the fixup at 0x1466c) is a real
   function but is absorbed by 0x147a8's extent.  Sketch: in `partition()`,
   when a `data-ptr` seed lies inside an existing function's range, split the
   range at the seed if `p.insns[seed - k]` is a terminator and the preceding
   bytes are filler.  A `wc1.symbols` entry for 0x14960 would then be legal.
2. **Save-slot format doc** (`docs/subsystems/save_format.md` section 1):
   cross-reference this page — 0x14670/0x146cc/0x14740/0x147a8/0x1498c/0x14ad8
   now have symbol names (`SaveFileChecksum`, `SaveFileFinish`, `SaveSlotPath`,
   `SaveSlotsScan`, `SaveSlotOpen`, `SaveSlotCreate`) and T3/T4 entries.
3. **Test harness** (`tools/wc1/cemu.py`): the Watcom 10.0a `sprintf`/`strlen`
   are segmented and fault in the flat emulator; a built-in model for
   `strlen` (and a `%d`-only `sprintf`) like the existing `memcpy` stub would
   make the save-slot functions (and every other clib caller) difftestable.
4. **Modules** (`analysis/modules.toml`): the range is still one module named
   `mod_13f60`.  The evidence above puts a boundary at 0x145e6
   (`DISPATCH.C` 0x13f60..0x145e6 and `DLGS.C`/`DLG_SET.C` 0x145e6..0x16390);
   renaming needs `tools/wc1/modules_names.py` (owner).
5. **Correction for `docs/subsystems/game_2c4e0.md`** (mod_2ced0 area):
   0x2e96c is *not* "the target-less order handler 0 in the table at 0x5158c".
   The order-0 handler is 0x13f60 (`OrderUpdateGone`, this area), which *calls*
   0x2e96c every tick; 0x2e96c itself is the unit-removal helper
   (`DrawListRemove`, owner → neutral, `flags`), i.e. UNIT.C code.  That page
   should link here instead of naming it handler 0.
