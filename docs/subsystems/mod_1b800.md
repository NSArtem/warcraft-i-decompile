# mod_1b800 (0x1b800..0x1bf80): the game-event sound layer

Symbols: `analysis/symbols/mod_1b800.toml`; C: `src/mod_1b800/` (one function
per file); header `src/include/mod_1b800.h`; tests `tests/test_mod_1b800.py`.
The range is the 18 functions of `analysis/modules.toml` (AGENTS.md says ..0x1c020;
0x1bf80.. is the next object).

## What it is

A thin sound layer between the game logic and the sound library (audio.md).
One core, **SndEvent** 0x1b800 (`id`, `unit`), turns an *event id* (1-based, 1..47)
into a sound slot for `SndPlay` 0x26958, and a set of small wrappers choose the
id for one game event (selection, order acknowledged, death, construction,
bullets, enemy near the town hall).  Nothing here changes game state except the
per-unit pending-sound byte (+9) and the alert cool-down (+0x18).

* With sound effects on (`opt_sfx_volume` 0x532bc != 0): `SndPlay(id-1)`.  With a
  unit argument the sound is dropped when the unit has flag 0x8 or 0x4000
  (main flags +0x10), flags2 0x100 (+0xe) or its tile is outside the visible
  15x11 window (`map_scroll_x/y`).  Id 0x1b ignores the unit (always audible).
* With sound effects off: the caption `snd_event_caption[id-1]` (0x52028) is
  shown in the message strip with `fn_19edc` 0x19edc (mode 0x24), if there is one.
  Captions exist only for ids 16..21 and 24..26 ('work complete', 'training
  complete', "we're under attack", 'village under attack', 'enemy approaching',
  'building destroyed').
* The sound slots are loaded per race by `SndEventsInit` 0x1b8d4 from
  `snd_event_table[scenario_race]` (0x520e8 -> lists 0x51ef8 human / 0x51f58 orc of
  47 resource ids) with `SndLoadTable` 0x267fc, so event id N is list entry N-1 of
  the race's list.  The lists differ only in the voices.

Unit/record facts used (offsets are the evidence): unit +9 is a *pending sound
id* that the animation-script opcode 0x10457 plays and clears (`xchg [edi+9],al`,
then SndEvent with the animated unit 0x50f7c); +0x18 is the under-attack alert
cool-down (4000 ticks); +0x36 (nonzero = the enemy scan ignores the unit).
UnitStartDeath 0x2d0e0 is, by its +0x52/+0x50 progress counters and the 0x80
flag at completion, the building-construction tick (not a death handler): it
calls SndConstructionTick every tick and SndWorkComplete at the end.

## T3 / T4 status

15 of 18 functions match under Watcom 10.0a (`/* codegen-compiler: 10.0a */`,
default OPT flags).  Spellings that were needed: the tile read as a dword view
`*(int *)((char *)&u->tx - 2) >> 16` (the original loads the dword at the
previous field and shifts), `px = px / 16` on the parameters themselves
(SndSummonAt: reuses the parameter registers), and in fn_1bd04 a NULL local and
an always-true `&& u != 0` that keeps the unit live in edx.

T4 (reference C + difftest on the compiled C vs the original under wc1.emu): the
three that do not match are a register-allocation difference of the same kind
(the original allocates the first coordinate to a different register than we
do), recorded per function in `t3_blocker`:

* SndEvent: x/y/scroll registers and the caption index addressing.
* UnitAlertSuppressArea and SndEnemyScan: the map clip + scan loops match in
  structure and in every instruction except the registers of x/y/tx and the
  in-place `shl`.  For SndEnemyScan all 24 declaration orders of x,y,w,h were
  tried; the unit-pointer copy, tx/ty locals and `h = w` spellings for the
  other.
