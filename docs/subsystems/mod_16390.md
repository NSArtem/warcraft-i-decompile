# mod_16390 (war.exe 0x16390..0x19020): the dialog engine, the UI event layer
# and the victory epilogue

Evidence: `analysis/symbols/mod_16390.toml`. Discovery: 54 functions,
`analysis/modules.toml` range `mod_16390` (the boundary comes from the 7 zero
bytes at 0x16389..0x1638f, i.e. linker padding after the setup menu).

## 0. What is actually here (and what is not)

The module range is coarse: it holds three groups of code that were separate
objects in the original build. The string pool slice the module detector used
(`0x56bd8` `[empty slot]`, `0x56be8` `The End`) belongs to the epilogue and the
edit-field code, not to unit placement.

**The placement/build UI is not here.** The strings `Select location.` 0x572dc
and `Unable to create unit.` 0x572ec are referenced from 0x22798 (+0x14f) and
0x229c8 (+0x48) only, i.e. the `mod_20c30` module (0x21c20..0x22xxx), not from
any function in 0x16390..0x19020 (`python3 -m wc1.xref 0x572dc`/`0x572ec`).
This area's `DialogRun` 0x180a8 is the generic modal box that those dialogs
would be built from, and `DialogItemHitTest`/`EditFieldRun` are the controls
they use, but the map-coordinate/tile-check/unit-creation code lives in
mod_20c30 (change request in section 9).

| group | range | evidence |
|---|---|---|
| dialog engine (DLGS.C) | 0x16390..0x1825c | descriptor resources loaded/relocated, 0x1c-byte item lists, two layers per dialog, modal loops |
| UI event layer | 0x182e4..0x1878c | event handler table 0x51770 entries, `event_handlers` 0x59400 slots |
| victory epilogue | 0x18790..0x19013 | `ofinale.war`/`hfinale.war` FLIC, `The End` credits; called only from main (0x1e32f) |

0x18488 `UiInputInit` and 0x184cc `UiEventPump` are already named in
`playflic.toml` (medium) and are not re-described here; the network twin
0x185b4 `UiEventPumpNet` is this area's.

## 1. The dialog descriptor (`Dialog`, resource-loaded)

`DialogLoad` 0x16694 loads a descriptor resource (`ResourceBegin(id,0)`,
`GdsAlloc(size)`, `ResourceRead(p,0)`), `DialogRelocate` 0x166bc turns the
stored offsets into pointers, `DialogCreate` 0x168b4 builds the screen layers
and `DialogFree` 0x16bdc tears everything down.

| off | type | meaning | evidence |
|---|---|---|---|
| +0x00 | word | layer index; the dialog owns layers `layer` and `layer+1` | written from `DialogRun`'s 4th argument at 0x180d9 (`mov [eax],cx`), used as a word index into `layers` at 0x1698a/0x16c04 |
| +0x02 | short | x | 0x180dc, `layers[layer+1].x` at 0x16965 |
| +0x04 | short | y | 0x180e0, `layers[layer+1].y` at 0x16981 |
| +0x06 | dword | parameter block pointer (`int *params`) | 0x180e4 stores the 5th argument |
| +0x0a | short | dialog bitmap width | set from the first art entry at 0x16a25 |
| +0x0c | short | dialog bitmap height | 0x16a2f |
| +0x0e | dword | dialog bitmap data (GdsAlloc w*h) | 0x16a42 |
| +0x12 | dword | art list (8-byte entries, -1 terminated) | 0x168bb, 0x16c2b |
| +0x16 | dword | second art/offset list (relocated 0x166c7; not otherwise read here) | 0x166c7 |
| +0x1a | dword | array of -1-terminated offset arrays | 0x1677e-0x167a3 |
| +0x1e | dword | callback block (see below) | 0x166e6 |
| +0x22 | dword | 10-byte entries (type, x, y, text) drawn at create time | 0x167ac, 0x16b2c |
| +0x26 | dword | item list (0x1c-byte entries, -1 terminated) | 0x167e9, 0x1701c |

Art entries (`DialogArt`, 8 bytes): `{short id; short kind; void *data}`.
`id == 0xf5` means "the shared dialog frame art" — `dialog_art_bm` 0x593e0 /
`dialog_art_data` 0x593e4 loaded by `DialogArtLoad` 0x1806c from resource 0xf5
(41604 bytes = 320*130 + 4, `resources.md`). Every other id is loaded with
`ResourceBegin`/`ResourceReadHeaderBody` (0x16927-0x16937).

The callback block at +0x1e has four indices relocated through the parameter
block (0x166e6-0x16754), `-1` meaning NULL:

| off | call | caller |
|---|---|---|
| +0x08 | selection changed | `DialogCallSelect` 0x174ac |
| +0x0c | dialog opened (called at the end of `DialogCreate`, after the item bitmap is cleared) | `DialogCallOpen` 0x16894 |
| +0x10 | finished? nonzero = yes (16-bit result) | `DialogCheckDone` 0x16f44 |
| +0x14 | dialog closing | `DialogCallClose` 0x168a4 |

`DialogCallOpen`/`DialogCallClose` are called with the **Dialog\*** (eax = d),
`DialogCallSelect`/`DialogCheckDone` with the **parameter block** (eax = d+6) —
0x16894 vs 0x174b6/0x16f51.

## 2. The parameter block (`int *params`)

The descriptor's +0x06 points at a caller-owned dword array (the setup menu's
parameter structs: `map_choice_params` 0x5160c, `army_setup` 0x51660,
`net_settings` 0x51638 in `mod_13f60.toml`). It has two uses, both by index:

* the callback block's indices select **function pointers** from it
  (0x166f1: `mov ecx,[params+idx*4]`);
* list controls store their **current selection** in it
  (`ListSelPrev/Next` 0x17430/0x1746c write `params[item->id]`,
  `ListSelectedText` 0x163a8 reads its low word).

So the first dwords of a screen's parameter struct are its state variables and
the later ones its callbacks; `map_choice_params` = `{selected map, 4 choice
callbacks, 3, refresh callback, ...}` fits that (mod_13f60.toml).

## 4. The modal flow

```
DialogRun(id, x, y, layer, params)        0x180a8
  DialogLoad(id) 0x16694 -> DialogRelocate 0x166bc -> DialogCreate 0x168b4
    art list -> layers[layer+1] (BitmapBlit), bitmap -> layers[layer]
    DialogCallOpen, draw the 0x22 texts, DialogDrawItems 0x16520
  save evt_mask + the 0x28-byte event_handlers block, install:
    event_handlers[0] = DialogKeyHandler 0x16c58
    [4] 0x59410 = DialogLeftPressHandler 0x16ca8
    [5] 0x59414 = DialogLeftReleaseHandler 0x16cbc
    [8] 0x59420 = DialogIdleHandler 0x16c8c
  palette restore if palette_faded
  DialogLoop 0x17e54
    per frame: UiEventPumpNet 0x185b4 (or the caller pumps), DialogPreviewCursor
               0x16f5c, ScreenUpdate
    key path:  last_key 0x593f8 (set by DialogKeyHandler) -> 0xd/0x1b finish,
               0x4800/0x7700/0x5000/0x7c00 -> ListScrollBy(+-1) 0x17c4c,
               item->hotkey match (or 0x7e) -> DialogActivateItem
    mouse path (while left button held, 0x593fc): DialogItemLoop 0x1700c
               hit test 0x16cc8, highlight on/off, ListSelectAtMouse 0x16eb0,
               auto-repeat via auto_repeat_delay 0x593ee -> DialogActivateItem
  restore evt_mask/handlers, DialogCallClose, DialogFree
  return dialog_result 0x593f2
```

`dialog_running` 0x593fa is the loop flag, `mouse_in_preview` 0x593f0 hides the
cursor layer while the mouse is over the map-preview rectangle 0x5175c,
`ui_net_forward` 0x5942c is set by the network pump (the peer plays the
dialog's keys) and suppresses the ctrl+M/ctrl+S toggles in `UiKeyDispatch`
0x182e4.

### Edit fields (`EditFieldRun` 0x17588)

Item types 7 and 0xb run a modal string editor on top of the dialog: the text is
copied into a `GdsAlloc(maxlen+1)` buffer with `[empty slot]` 0x56bd8 for an
empty value, padded with spaces, drawn by `EditFieldDraw` 0x174c0 (text plus a
0xf6 caret bar at `edit_cursor` 0x593ec). Keys handled: left/right/home
(0x4b00/0x4d00/0x4f00), insert/delete (0x5200/0x7b00/0x7e00), up/down as
line start/end of the 40-character field (0x4700/0x4800/0x5300/0x7600),
backspace (8), enter (0xd) and escape (0x1b); printable characters pass the
`edit_char_hook` filter 0x5176c (default `EditDefaultCharFilter` 0x16390,
printable ASCII 0x20..0x7e; the settings dialogs swap in the phone/number
filters, mod_13f60.toml). On enter the buffer (trailing spaces trimmed) is
copied back to the item's text pointer and 1 is returned.

## 5. The UI event layer (0x182e4..0x1878c)

`EvtGet`/`EvtProcess` deliver a 12-byte `Event` `{word type; word sub; short x;
short y; byte scan; byte mods; word key}` (input.md; key-down posts type 0x80
with sub 0, key-up type 0x100 with sub 2, 0x31215). The pump dispatches it
through `event_handler_table` 0x51770 (ten dwords indexed by `ev->sub`):

| sub | handler | slot(s) it calls |
|---|---|---|
| 0 | 0x182e4 `UiKeyDispatch` | `event_handlers[0]` (key handler) |
| 3 | 0x18458 `UiMouseMove` | `event_handlers[3]` 0x5940c `status_mouse_callback` |
| 4 | 0x18398 `UiButtonPress` | sets bit 0, calls [4] 0x59410 |
| 5 | 0x183e8 `UiButtonRelease` | clears bit 0, calls [5] 0x59414 `status_frame_callback` |
| 6 | 0x18398 `UiButtonPress` | sets bit 1, calls [6] 0x59418 |
| 7 | 0x183e8 `UiButtonRelease` | clears bit 1, calls [7] 0x5941c `status_click_callback` |
| 8 | 0x18470 `UiFrame` | `event_handlers[8]` 0x59420 (dialog idle / outro tick) |

`UiButtonPress` ignores a second button while `ui_button_bits` 0x5942e is
nonzero (0x18399). `UiKeyDispatch` normalises the modifiers, then handles
scancode 0x29 (` int3`), ctrl+M (0x432, `SndToggleMusic`) and ctrl+S (0x41f,
`SndToggleSfx`), skipping them when `ui_net_forward` is set, and otherwise calls
`event_handlers[0]`; every path ends in `fn_13e94` (0x13e94, codegen_promo).

`event_handlers` 0x59400 is a 10-dword block (0x28 bytes); slots 3/5/7 are the
status panel's callbacks (`status.toml`), 0/4/5/8/9 are this object's, and
`UiInputInit`/`UiEventPump` are the playflic-named generic versions.
`UiEventPumpNet` 0x185b4 is the two-player twin: it sets `ui_net_forward = 1`
and takes events from `NetSendLocalEvent`/`NetQueryRemoteEvent` instead of
`EvtGet` (the same split as the save/load dialogs, save_score.toml).

## 6. The victory epilogue (0x18790..0x19013)

`main` 0x1e158 calls `OutroPlay` 0x18fb0 at 0x1e32f when the campaign is won
(game_mode set by the victory check around 0x1e2dc).

```
OutroPlay 0x18fb0
  hide the cursor layer (layers[cursor_layer_id].active = 0)
  outro_is_orc = (scenario_race == 1); cur_font = &alt_font (0x59220)
  OutroPlayFlic 0x188b4
    name = outro_is_orc ? 'ofinale.war' 0x51798 : 'hfinale.war' 0x517a4
    FlicOpen(0xef)/FlicRewind, two 0xfa00 buffers
    layer 0xe = 320x200 FLIC bitmap (BitmapBlit), palette marker 'BIF' at 0x591f3
    art resource 0x1cf (orc) / 0x1c? ; sound tables 0x517b0 / 0x517b6
    music 0xd (orc) / 0xc (human); frame loop, one frame per 2 OutroTick calls,
    sound cues on frames 0xd/0x17/0x1a/0x37/0x3f, exit when the cursor band
    reaches y 0x1e (0x18a4d)
  OutroShowCredits 0x18b64
    orc: GRP art resource 0x1ce into layer 0xf; text resource 0x1d3 read through
    the text-box reader 0x21d0c with OutroDrawLine 0x187d4 as the line callback
    scroll the text up 14 lines per page (OutroDrawTextPage 0x18810), animate the
    GRP with OutroShowFrame 0x18890, then draw 'The End' 0x56be8 centred at y 0x80
    and wait for OutroEnd 0x187c8 (any key/click) -> outro_done 0x59430
  CursorLayerShow
```

`OutroTick` 0x187a4 is the frame callback in `event_handlers[8]`; `outro_tick`
0x59436 counts tick callbacks and `outro_frame` 0x59434 the animation frames.
`alt_font` 0x59220 is a Font record in BSS filled at run time (the image shows
zeros); the credits also use `palette` 0x58f20 and resources 0x1ca..0x1d3.

## 9. Open questions / change requests

* **The area assignment's placement strings are in mod_20c30.** `Select
  location.` 0x572dc and `Unable to create unit.` 0x572ec are referenced from
  fn_22798+0x14f and fn_229c8+0x48 (mod_20c30). The placement/build UI should
  be analysed there; this area supplies the modal box it calls (0x180a8) and
  the controls.
* **`ShowMessage`'s prototype (gamedlg.toml)** calls the box as
  `ShowMessage(text, width 0x176, height 0xa)`, but 0x176 is the dialog
  descriptor **resource id** and 0xa is the **layer index** (`DialogRun`'s
  4th argument goes to `d->layer`, 0x180d9). Suggest renaming those parameters
  to `dlg_id`/`layer`.
* **`playflic.toml`'s `intro_layer_top`** is now `cursor_layer_id` in the DB
  (0x5aa78) while `src/include/playflic.h` still declares
  `intro_layer_top`; the header should follow the DB.
* **`status.toml`'s fourth callback** (0x59424) is named `event_pre_callback`
  here (called with eax=0 once per event by both pumps, 0x1857f/0x18756);
  status.toml's test stub calls it `_status_event_callback` — one name should
  win.
* **`fn_13e60` (0x13e60)** is the tail target of `UiFrame` 0x18470 and the
  entry after `fn_13e94`; it has no symbol entry yet (codegen_promo area).
  Without it 0x18470 cannot be resolved by `wc1.match`.
* **Shared data ownership**: `cursor_hotspot_x/y` (0x5aa60/0x5aa62) are used
  by graphics (`CursorSetImage` 0x317b0, `CursorMoveTo` 0x330a0) but were
  unnamed; they are declared in this TOML. The graphics area should adopt them
  (or rename and this area follows).
* **`layers` (0x5aa90) and `cursor_layer_id` (0x5aa78)** are playflic's
  entries; the struct in `src/include/mod_16390.h` matches the 18-byte layout
  graphics documents.
