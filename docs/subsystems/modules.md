# Modules: object-file boundaries of the code object

Result: `analysis/modules.toml`, 159 contiguous ranges covering 0x10000..0x4212b
(generated by `python3 -m wc1.modules_gen`; rules in `tools/wc1/modules_scan.py`,
curated names in `tools/wc1/modules_names.py`; test `tests/test_modules.py`).
Boundary confidence: 140 medium, 19 low. Names: 21 medium, 18 low, 120 generic
(`mod_XXXXX`, speculative).

## Evidence used

1. **Zero-fill alignment (main signal).** Game modules are PARA-aligned. Between
   two functions of one module the compiler pads with `nop`, `mov eax,eax` or
   `lea eax,[eax+0]` (3 patterns, never more than 3 bytes, never zero); between
   modules the linker pads with zero bytes up to 16. A 16-aligned function start
   preceded by 1..15 zero bytes is a module start (`zero16`, 133 of them, 58 in
   the game range 0x104b0..0x30bd0). Narrower zero gaps before 2/4-aligned
   starts (hand asm, library objects) are the same signal, low confidence
   (`zero2`/`zero4`, 18).
2. **Independent cross-check.** The string pool 0x569d0..0x58440 is laid out in
   link order: of 179 pool items only 7 are referenced by more than one function
   and no pool item is referenced from two different zero16 chunks (0
   inversions between chunk windows), so the zero16 partition is consistent
   with the data object's module order. The `A` (_DATA, 0x50000..0x56000) and
   `C` (_BSS, 0x58500..) chains also form staircases but are polluted by globals
   and were not used as proof.
3. **setup.exe sharing** (`wc1.modules_setup`): setup.exe is a second 32-bit
   Watcom program; 328 functions of war.exe are byte-identical there (fixups and
   external branch targets masked): the AIL library, the Watcom runtime and a
   hand-asm helper module (0x3024e..0x30bc9, 17/18 identical). This marks
   library/shared code and separates it from game code.
4. **Other areas:** AIL = [0x34d83,0x3aac0) with sub-ranges (audio.md); resource
   functions (resources.md); libsig matches (clib.toml).
5. Structural facts: `int N; ret` stub table 0x3b58e..0x3b88e (256 stubs, one
   library object); asm tile/sprite blitters 0x10010..0x104b0 (odd addresses, 320-wide
   destination stride); in-code data tables (pointer/jump tables inside a
   module's code, e.g. at 0x145e6) are *not* boundaries.

## Layout

| Range | Contents |
|---|---|
| 0x10000..0x10010 | BEGTEXT stub of the startup object |
| 0x10010..0x104b0 | 3 hand-asm blit modules (tiles, sprites/RLE, stubs) |
| 0x104b0..0x3024e | ~58 game modules (C, 16-aligned) |
| 0x3024e..0x30bd0 | hand-asm module shared with setup.exe |
| 0x30bd0..0x30c50 | game stub; `FatalError` 0x30bf0 (analysis/symbols/modules.toml) |
| 0x30c50..0x34d83 | runtime / graphics-lib / resource objects, one function per object where zero16 |
| 0x34d83..0x3aac0 | Miles AIL (core, MDI, timer, DIG, VOC) |
| 0x3aac0..0x4212b | Watcom clib objects (int-stub table 0x3b58e, LZSS 0x41550, FPE handlers 0x41b77...) |

Named game ranges (all from content, see evidence in the toml): INIT.C
0x1d2a0 (medium; contains verified InitPaths), SCORE.C 0x24e50 (medium), and low
confidence BULLET.C 0x119c0, CMD.C 0x123f0, HARVEST.C 0x1cd50, GAMEDLG.C
0x1a3c0, NETWORK.C 0x1f050, PACKET.C 0x214b0, PLACEBOX.C 0x21df0, PLAYFLIC.C
0x22c50, SAVE.C 0x23ec0, SND.C 0x26320, SPELL.C 0x27670, STATUS.C 0x27b20.
The chunk order from HARVEST onward follows the guide's alphabetical list
(HARVEST < INIT < NETWORK < PACKET < PLACEBOX < PLAYFLIC < SAVE < SCORE < SND <
SPELL < STATUS), which supports but does not prove the names. The `'xxx:N'`
tag strings (attack:1, bullet:6, harvest:7, spell:1, dispatch:5...) are default
entries of handler tables passed to `FatalError`; they name *handlers*, so
they are weak evidence for module names.

## Open questions

* A module whose code ends exactly 16-aligned leaves no zero gap. 117 `none16`
  and 12 `data16` starts are such possibilities (expected true count ~5-8);
  nothing reliable separates them (call/data locality gave ~4.6x likelihood
  ratio at best). Large chunks likely holding several modules: 0x13f60 (68
  functions: dispatch, modem-setting helpers, save-slot strings), 0x16390,
  0x1f050, 0x27b20, 0x295d0, 0x2ced0, 0x2efd0.
* Many generic library chunks (0x30c50, 0x33520, 0x33b00, 0x3b980..., 0x409a0,
  0x41800) are multi-object hand-asm regions: splitting them needs OW2 library
  unit matching (clib area).
* Guide graphics modules (BMP*, DFL*, EVT*, FNT*, VID*...) are not placed:
  0x19020 (FLIC header/frame magic 0xaf12/0xf1fa) and 0x30ea0 ('evt lock') are
  the only anchors.
* The discovery's 256 `int N; ret` stubs are listed as 256 functions.
