# Game logic: CMD.C (0x123f0..0x12b80) - the terrain cache and typed commands

Module range `CMD.C` in `analysis/modules.toml` (18 functions, 0x790 bytes).
Symbols: `analysis/symbols/cmd_123f0.toml`; C: `src/cmd_123f0/`,
declarations `src/include/cmd_123f0.h`; dumps
`build/cmd_123f0/{dump,ctx,xref,neigh}.txt` from `python3 -m wc1.cmd_123f0_dump`.

The range holds two unrelated groups (see "Module boundary?" at the end):

| range | what it does |
|---|---|
| 0x123f0..0x127ff | keeps the scrolled **terrain cache** in step with `map_scroll_x/y` |
| 0x12800..0x12b80 | parses **typed commands** (cheat phrases, `orc<N>`/`human<N>`) |

Nothing in this range touches the unit order bytes at `unit+0x1f/0x20/0x21`:
the orders layer is `mod_2ced0` (see `docs/subsystems/game_2c4e0.md`). This is
the *player* command layer - the text the player types into the message window
and the command line, plus the view scrolling that the scroll command performs.

## 1. The terrain cache

`terrain_cache` (0x58574, graphics.toml) is a 64 KB byte buffer that holds the
map around the view: tile (x, y) starts at `((y * 256 + x) * 16) mod 0x10000`,
which is exactly the offset `MapDrawTerrain` (0x10010) copies the 240x176 pixel
window from. A tile is 16x16 px = 2x2 8x8 minitiles, written by
`MiniTileToCache` (0x1007c) at +0, +8, +0x800, +0x808. The view shows 15 x 11
tiles, so

* `TerrainCacheRunX` (0x124e8) paints 15 tiles of one row (`cmp eax,0xf`),
* `TerrainCacheRunY` (0x12524) paints 11 tiles of one column (`cmp eax,0xb`),
* `MapViewInitLimits` (0x123f0) sets `map_scroll_x_max` = 49 = 64-15 and
  `map_scroll_y_max` = 53 = 64-11,
* `MapViewScrollUp/Down/Left/Right` (0x125c4/0x12620/0x12688/0x126e4) move
  `map_scroll_y/x` (clamped to 0 and to the maxima) and repaint only the rows or
  columns that the slide exposes - `tile_cache_top` (0x58590) and
  `tile_cache_left` (0x58592) remember which tile row/column the cache currently
  starts at, and are walked towards the new scroll position (down:
  `TerrainCacheRow(top + 11)`, right: `TerrainCacheColumn(left + 15)`),
* `MapViewSetScroll` (0x1274c) clamps a requested (x, y) and rebuilds all 11
  rows. Its callers are the map loader (0x1b42e), `fn_1b11c` which tail-jumps
  with (x-7, y-5) to centre the 15x11 view on a tile (0x1b126), `fn_19d68`
  which restores a saved view (0x19d82), and the viewport callback 0x1ef48.

The scroll commands come from `fn_259d8` (0x259d8), which receives the (dx, dy)
of one scroll step: negative dy -> 0x125c4, positive -> 0x12620, and likewise
for x at 0x25a86/0x25a94.

The tile words come from `tile_map` (0x58584, allocated 0x2000 = 4096 words by
the map loader at 0x1b1e0): bits 0..10 are the graphic index into
`fog_cell_table` (0x5858c, allocated 0x4000 = 2048 entries of 4 minitile ids),
bits 11..15 are per-tile state that 0x105d0 and 0x2ba50 preserve while changing
the graphic. **Note for the graphics area:** `fog_cell_table` is used here as
the *terrain tile -> minitile* table (its name and its `cell & 0x1f` use in
FogDrawCell describe only the overlay side, and the 2048-entry size only fits
the 11-bit tile index).

`FogMapObscure` (0x12438) ORs 0xa0a into every one of the 4096 `fog_map` words
at map load (0x1b418, only when word [0x5152c] == 0): the low 5 bits 0x0a are
the "solid black" overlay that `FogDrawCell` (0x1af32) special-cases. Its
mirror `FogMapClear` (0x12404, writes 0 = no overlay) has **no reference at all**
in the image - dead code in v1.22h.

## 2. Typed commands and cheat flags

`CmdProcessText` (0x12b50) is the entry point: `strlwr(text)`, then
`CheatCodeCommand` (0x12a2c), then `CheatScenarioCommand` (0x1295c); it returns
1 if either handled the text.

* **message window** - `fn_1b690` collects typed characters into the buffer at
  0x59652; on Enter it copies `cheat_flags` (0x51214) to the stack, calls
  `CmdProcessText` (0x1b724) and, if it matched, sends the new flag word to the
  peer with packet type 0x10 (`fn_21c44`); otherwise the text goes out as chat
  packet 0xf (`fn_21c68`, "message sent to opponent"). The peer applies it in
  `fn_215f0` with `mov eax,[edi+3]; call SetCheatFlags` (0x21826).
* **command line** - `fn_1d740` walks `__argv+4`, lower-cases each argument and
  calls `CmdProcessText` (0x1d772) with a stack copy of the flags, then
  `SetCheatFlags` after every argument (0x1d784).

### the obfuscated cheat words

`CheatCodeMatch` (0x12800) compares the input with an entry of the pool at
0x51218: byte *i* of an entry is `plain[i] XOR (1 << (i % 8))`, the key starting
at 0x01010101 and rotating left once per matched character (`_rotl` at 0x30c68,
0x1282e-0x1283a). It returns the *raw* pool byte where the input ended, i.e. 0
only at the entry's own NUL. Note the trap: an encoded `' '` at index 5 (or 13,
21, ...) becomes a raw 0x00, which is why the strings look truncated to a naive
NUL split - and also why typing a prefix such as `yours` or `there` matches.

Decoded (the length of each entry ends exactly at the next referenced address):

| pool offset | cheat phrase | flag bit toggled |
|---|---|---|
| 0x00 (0x51218) | `corwin of amber` | 0x80000000 (`flags[3] ^= 0x80`) |
| 0x10 (0x51228) | `yours truly` | 0x100 (`flags[1] ^= 0x01`) |
| 0x1c (0x51234) | `crushing defeat` | 0x80 |
| 0x2c (0x51244) | `there can be only one` | 0x04 - only when the *global* `cheat_flags` bit 31 is set (test at 0x12ad0) |
| 0x42 (0x5125a) | `pot of gold` | 0x20 |
| 0x4e (0x51266) | `eye of newt` | 0x08 |
| 0x5a (0x51272) | `iron forge` | 0x10 |
| 0x65 (0x5127d) | `sally shears` | 0x01 |
| 0x72 (0x5128a) | `hurry up guys` | 0x02 |
| 0x80 (0x51298) | `ides of march` | 0x40 |

Independent confirmation: the Insider's Guide (docs/REFERENCES.md R1) documents
"the cheat code `eye of newt` ... activate all spells (of the respective
scenario) and receive unlimited mana. Enter all cheat codes in the message
window" - exactly the `fn_1b690` -> `CmdProcessText` path and the bit that
`SetCheatFlags` uses to write the six per-player spell bytes.

### what the bits do

`SetCheatFlags` (0x1284c) stores the word and applies the one-shot effects:

* 0x08 (`eye of newt`): for p = 0..1 with byte [0x5008c+p] == 0, set the six
  per-player bytes 0x50017/0x5001c/0x50021/0x50026/0x5002b/0x50030 (+p) to 1 -
  the six strategic spells per side (the guide's count).
* 0x10 (`iron forge`): same players, set 0x50008/0x5000d/0x50012/0x50035 (+p) to
  2 - level 2 of the four weapon/armour upgrades the guide describes.
* 0x20 (`pot of gold`): clears itself, then adds 5000 to dword [0x50060+4p] and
  10000 to dword [0x50074+4p] for the five players (the resource arrays the
  harvest code and the 0x190 = 400 victory goals use).
* 0x40 (`ides of march`): stores `game_mode` (0x59616) = 10 when
  `net_play_flag` (0x52586) is 0. With the bit *clear*, mode == 3 and
  [0x5a7c2] == 0, it prints `cheat enabled you wascally wabbit` (0x569ec) or
  `cheat disabled` (0x56a70) through 0x19edc, chosen by old > new flags.

Bits that are only read elsewhere: 0x01 `sally shears` -
`ViewportLayerCallback` skips `FogDrawViewport` (0x1b05e), and the fog/visibility
helpers 0x13360/0x1346c/0x1357c/0x2d650 test it; 0x02 `hurry up guys` -
0x1435c skips the countdown at unit+0x3f, `UnitUpdateAll` 0x2d2a6 skips the
decay timer, 0x115ba/0x11660 similar; 0x04 `there can be only one` - 0x104b9
substitutes 200 (= the whole unit array) for the per-type count; 0x80
`crushing defeat` and 0x100 `yours truly` - the win/lose tests 0x2f4c0/0x2f540/
0x2f694 take their forced-defeat / forced-victory branches.
`fn_195ac` (scenario start) resets the word with `and [0x51214],0xa4000000`,
keeping only bits 22, 30 and 31.

`CheatScenarioCommand` (0x1295c) needs the developer bit: `strncmp` against the
plain strings "orc"/"human" (0x512a6/0x512aa), `strtoul` for the number (1..12),
then `scenario_race` (0x50088) = 1/0, `scenario_number` (0x50d82) =
120+2(n-1) for orc or 119+2(n-1) for human, and `game_mode` = 5 (the value the
scenario picker uses). In a link game (`net_play_flag`) it accepts the text but
changes nothing.

## 3. Codegen: this object needs `-oa`

> **Watcom 10.0a (2026-11-18).**  With the original compiler (docs/subsystems/compiler.md)
> CMD.C's flags are `-s -ot -oa -ol -4r -zp2`, and every built file of the area carries them
> plus `codegen-compiler: 10.0a`.  10 of the 18 functions are T3: the six below and four former
> reference files that only 10.0a matches - FogMapObscure 0x12438 (`fog_map_obscure.c`),
> MapViewSetScroll 0x1274c (`map_view_set_scroll.c`, only with `-ol`), CheatCodeMatch 0x12800
> (`cheat_code_match.c`) and CmdProcessText 0x12b50 (`cmd_process_text.c`).  CheatCodeCommand
> tests the developer bit through the bitfield `cheat_flags.f.dev`: 10.0a promotes the union-byte
> compare `b[3] & 0x80` to `and eax,0xff` but emits the original's `test byte [..],0x80` for the
> bitfield.  Their T4 tests still run against the same C.  The OW2 analysis below is history.

The style is the usual game-code OPT one (no frame pointer anywhere in the
range, only `sub esp,byte 4` locals at 0x124eb/0x12527/0x12960), so
`docs/subsystems/codegen.md` classifies it as OPT - but the flags that
reproduce it differ.

`docs/subsystems/codegen.md` calls the game default OPT =
`-s -ot -ol -4r -zp2`; for CMD.C that set matches only `MapViewInitLimits` (two
word stores) and is 5-90 bytes off everywhere else, while
    -s -ot -oa -4r -zp2

matches six functions exactly (`wc1.match`, also in `tests/test_cmd_123f0.py`):
0x123f0, 0x125c4, 0x12620, 0x12688, 0x126e4, 0x12a2c. `-oa` (relaxed aliasing)
is what lets the compiler keep `tile_cache_top`/`tile_cache_left` in a register
across the `TerrainCacheRow` calls and reload it after them - exactly what the
original emits (`mov dx,[0x58590]` right after the call at 0x1260b). Without `-oa`
the same sources are 45-90 bytes off, and adding `-ol` back is harmless for five
of them but breaks CheatCodeCommand (21 bytes), so the object's set is
exactly `-s -ot -oa -4r -zp2` and every file in `src/cmd_123f0/` carries it in
its header. Change request for the shared docs is in the area report.

Remaining differences in the other twelve functions are the documented backend
issues: V1/V4 (16-bit promote vs narrow in the loop tests of 0x12404/0x12438/
0x124e8/0x12524/0x1274c), V3 register roles (0x12800 and 0x12b50 differ only by
`ebx`<->`ecx` for two values - 22 and 5 bytes), V5/V10 loop layout
(0x12404 is one of codegen.md's own examples).

### Model difftests: the twelve near-misses are behaviour-verified

Because OW2 cannot reproduce them byte-for-byte, the other twelve functions are
verified by differential execution instead (`wc1.emu`, original against a Python
model of the reconstruction) - `tests/test_cmd_123f0.py::test_fog_map_loops`,
`test_terrain_tile_to_cache`, `test_terrain_cache_runs`,
`test_terrain_cache_row_column_use_the_scroll_origin`,
`test_map_view_set_scroll_clamps_and_rebuilds`,
`test_map_view_scroll_up_paints_the_exposed_rows`,
`test_cheat_code_match_against_the_real_pool`, `test_cmd_process_text_difftest`,
`test_set_cheat_flags_difftest`, `test_cheat_scenario_command_difftest`.  Each
of the 18 entries in `analysis/symbols/cmd_123f0.toml` therefore carries
`verified` with a `match:` or `difftest:` citation, and
`test_verified_entries_are_mechanically_checked` keeps that honest.

The difftests are also where the *semantics* are pinned down: `SetCheatFlags`
really adds 5000/10000 to the five players' resource arrays and clears its own
bit, writes 1 into rows 3..8 and 2 into rows 0,1,2,9 of the 10x5 per-player
table at 0x50008, sets `game_mode` 10 for "ides of march" only in a single
player game, and prints "cheat enabled you wascally wabbit"/"cheat disabled"
through 0x19edc; `CheatScenarioCommand` really maps `orc5` to scenario 128 and
`human5` to 127 with `game_mode` 5; `CheatCodeMatch` matches a phrase, rejects a
wrong character and accepts the prefix in front of an obfuscated space.

## 5. Module boundary?

0x123f0 is preceded by 11 zero bytes (a real object boundary) but the two groups
share nothing: different data (0x58574..0x58596 view state vs 0x51214/0x51218
cheat words), no cross calls, and only group B references the string pool slice
0x569ec..0x56a71 that modules.toml cites as CMD.C's evidence. The cheat codes
are commands; the terrain-cache functions are view scrolling. If `modules_gen`
supported a "none16" split here (0x12800 is 16-aligned and fn_1274c ends exactly
at 0x127ff), group B (0x12800..0x12b80) would be the better candidate for the
name CMD.C and group A would need a new one. Reported, not changed.

## 6. Open questions

* What `tile_map` bits 11..15 mean (0x105d0 changes them by +/-1..20 and calls
  0x2c2c4; the fog/visibility code in mod_2bxxx owns that story).
* Who is supposed to call `FogMapClear` (0x12404) - dead in this build.
* `cheat_flags` bits 22 and 30 (kept by 0x196cd) are never set in this range;
  0x16218 stores a whole word from the game-options code.
* The per-player table at 0x50008 (ten rows of five: rows 3..8 behave like the
  six spells, rows 0,1,2,9 like four upgrades), 0x50060/0x50074 (the two
  resource counters), [0x5008c] (the per-player gate both cheats test) and
  0x5a7c2 are entered in `cmd_123f0.toml` under the repo's placeholder naming
  (`dat_50008`, ..., confidence `low`) purely so the SetCheatFlags
  reconstruction compiles; the area that explains them should rename them.
* What `game_mode` = 10 ("ides of march") does in the main loop (0x2fcfc reads
  the dword at 0x59614 repeatedly); no other code stores 10.
* Matching (not just behaviour-verifying) 0x1284c/0x1295c additionally needs the
  OW2 register-assignment gap closed, and 0x1284c's `[0x5008c + player] == 0`
  test still has no interpretation.
